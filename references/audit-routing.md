# 自适应全维审计路由

适用协议：`LT-2026-08-21.11`

普通高风险、跨模块、公共契约变更或多功能项目终审读取本文件；命中底层架构触发时同时读取 [foundation-gate.md](foundation-gate.md)。只有命中下方正式审计触发项的普通任务才启动一个无历史、对产品文件只读、独立于设计者和实现者的 SOL 审计代理，执行一次终审并在集中修复后统一复审一次；“触发与跳过”的跳过项优先。底层任务使用独立 SOL Codex `ultra` 先审架构契约，实施冻结后由同一审计角色每轮完整统一审计，直到 PASS 或 BLOCKED。只有用户已经运行的原生 `/review` 同时给出对应契约要求的冻结指纹、矩阵状态、专项触发表、定位证据和总判定时，才可视为本次审计；否则其结果只作为证据。本文件不主动先运行覆盖不足的原生审查再追加 SOL。普通审计覆盖五项核心维度并只展开被变更触发的专项维度；底层审计使用 foundation-gate 的完整矩阵。安全维度按本文件触发表最小展开；不默认运行第三方安全插件或全域安全扫描。

任务启动以及跨日、长暂停、上下文压缩/恢复、移交或已知 skill 更新后，审计者在继续前重读当前 `SKILL.md`、本文件和任务引用；任务包协议版本不匹配时停止并回报，不凭旧摘要继续。

## 审计次数

- 命中正式审计触发项的普通完整交付只运行一次正式全维终审，集中修复后只运行一次统一复审。SOL 池最多 6 个同时活跃只是独立任务的滑动容量，不改变本契约：一个冻结变更集的每次审计只能由一个 SOL 完成，实现批次、单个功能、文件、维度、专项和每次小修不分别启动 SOL 审计。
- 普通终审必须等到代码、配置、迁移、当前状态项目索引、测试、基准/构建等适用执行产物稳定后再创建，并读取命中的历史日志；当前重大改动日志在审计后写入，不为该日志再开审计。不得提前创建普通审计 SOL 等待后续输入。底层任务按 foundation-gate 在架构契约冻结后先审架构门，搭建完成并冻结后再审实现门。
- 测试、类型检查、静态分析、基准、剖析、构建和界面验证是终审输入，不算独立审计，也不得各自生成重复的 LLM 复审。
- 只有下一步会执行不可逆数据变更、真实环境切换，或继续实现会显著放大已知重大损失时，才允许在危险动作前做一次最小范围中途审计；它不得顺手审查未冻结的其余项目，最终仍需一次整体终审。
- 普通首轮终审发现问题时，审计 SOL 必须先按 [dispatch-contracts.md](dispatch-contracts.md#sol-审计修复契约) 交付唯一完整修复契约，并为每个根因批次给出能力门证据和唯一执行者。`LUNA_GATE=PASS` 的有界批次由对应强度 Luna 集中修复；未通过且无法继续冻结的最小不可分关键切片由与设计者/审计者分离的实现 SOL `max` 修复。不得由主控或 Luna补做产品、架构、接口或算法决定，审计者不得亲自修复。之后用一个 SOL 回合一次性复审全部未关闭编号及合并影响面，不得逐问题、逐文件或逐维度复审。时间紧邻且总输入更小时复用原审计者，否则用无历史最小闭环包。若修复改变核心架构、公共契约或扩大变更集，该唯一复审回合扩大为完整终审，而不是额外再开一个回合。
- 普通自动返修后只允许上述一次 SOL 复审；仍有问题或证据不足时立即停止普通 SOL 消耗，保持“不通过/证据不足”并把问题、失败证据和已尝试修复交回主控，而不是宣告通过、换审计者重试或无限循环。底层任务不受这一普通限制：每轮 FAIL 先交完整唯一修复契约和执行者判定；架构门的机械文档修订由通过能力门的 Luna `max` 执行，架构决定/契约修订由原设计 SOL Codex `ultra` 执行；实现门中，通过能力门的有界批次由 Luna `max` 执行，其余最小不可分关键切片由独立实现 SOL `max` 执行。重跑确定性门、重冻结并由同一审计角色继续完整统一审计，仅在 foundation-gate 的 BLOCKED 条件成立时停止。

## 触发与跳过

先用本节条目判定是否创建正式审计；下文“按变更触发的专项维度”只扩展一个已经被本节触发的审计，单独命中专项触发表不会自行创建 SOL。若专项事实同时证明公共契约、高风险状态流、底层重构或多功能集成成立，则按对应本节条目触发。

- 纯文档、格式化或机械生成物只有在不改变任何可执行行为、公共契约/schema、配置语义、迁移、构建或发布事实时才跳过正式审计；实现者运行适用检查并由主控检查 diff。
- 普通局部改动只有同时满足以下条件才按跳过项处理：低风险且仅影响内部实现；未命中本节后续任何底层、混合、高风险或多功能触发项；不改变认证/权限、支付、迁移、并发、数据一致性、公共 API、跨模块状态流、外部依赖或部署运行流程。任一条件未知时不得使用本跳过项，必须按实际命中的后续触发项路由。满足时由实现者自检、运行相关测试并由主控检查 diff，不调用插件或 SOL。
- 底层架构触发（新项目骨架，或模块系统、跨模块公共契约/公共接口底座、全局生命周期/资源所有权、持久化/迁移基础设施、IPC/事件总线底座、权限底座、插件系统、运行时/构建发布底座的建立或重构）：必须执行 foundation-gate 的架构门和实现门。运行时/构建/发布底座仅指共享构建图、依赖闭包机制、产物组合根、发布 gate、更新/回滚流水线或平台抽象的建立/重构；单个依赖、版本、配置键或产物成员变化不改变这些机制及契约时不触发底层门。事实不足时先运行 `LUNA_FACT_GATE` 有界取证再判定。普通 API 方法/端点、单个模块、局部生命周期及不改变底座契约的功能迭代走普通风险路由，不因跨文件而触发底层门。
- 混合交付中的普通功能若依赖、改变或验证底层契约，或共享写集、运行状态、迁移、集成验收，则纳入同一底层冻结变更集。只有公共契约/调用依赖交集为空、精确文件与符号写集不重叠、进程/端口/锁/数据库/迁移/缓存等状态资源不共享、两部分可独立执行验收且无需对方产物四项均有可复核证据时才分开审计；任一项重叠或未知即合并。
- 认证、权限、支付、迁移、并发、数据一致性、公共 API、跨模块状态流或高影响部署变更：因后果与契约风险，对冻结变更集运行完整核心审计及被触发的专项维度；不是为了额外扩大安全检查范围。
- 普通多功能项目集成：只在最终变更集稳定后运行一次整体审计，集中修复后统一复审一次；实现期间不按批次审计，已审且未受影响的范围不重审。
- 没有有意义基线的普通纯新建项目不做全仓式扫描：以全部 `R-/F-`、对应逻辑承载路径、公共契约、失败路径和触发专项为审计范围，确保每个 `R-/F-` 都有实现与验证证据；命中“新项目骨架”时改用 foundation-gate，不跳过底层矩阵；两者都跳过生成物、依赖、纯样板和无关文件，也不伪造差分结论。

## 冻结输入

主控先冻结并提供最小充分任务包：

1. Git 仓库提供基线提交/引用、完整 `git status --short` **元数据清单**、任务范围 staged/unstaged/untracked diff 摘要/内容位置，并列出不属于本任务的用户变更；无 Git 项目提供任务范围文件清单、稳定前后副本/清单（存在时）和文件哈希，不强制初始化仓库。不得把“完整清单”解释为把所有文件内容复制进任务包。
2. 原始用户需求、后续修改、明确非目标和约束，以及全部规范化 `R-` 验收语句、相关 `A-/F-/T-`、稳定接口、不变量、`必读.md` 和命中的重大改动日志位置；审计者必须独立验证 `原始需求 → R-` 完整性。
3. 变更文件、关键符号、调用者/被调用者、迁移或回滚边界、测试命令和原始关键结果；按触发维度再提供性能基线、兼容矩阵、部署/回滚、用户流程、依赖或平台证据。
4. 任务范围产品文件与当前状态索引的指纹。审计期间这些文件变化则结果作废；预定审计报告写入和终审后的重大改动日志不计入指纹。
5. 主控先给出一行维度触发表：`核心=全开；专项=<名称:触发证据 | 不适用>`。审计者发现遗漏触发项时可以补开，但不得无证据展开全部专项。任务另给 `WANXIANG_ROUTE=ON|OFF|N/A` 及触发证据；只有无 GUI 工作时可 N/A，ON 时核对冻结的万相契约与最新运行验证，OFF 时不得把行为修复扩大成换肤或设计系统重审。

底层任务还必须提供：架构契约门或实现门标识、1-14 矩阵清单、阶段化证据类型、确定性门命令及关键原始结果、每批执行者/Luna 能力门证据、修复契约历史、append-only 回合/问题账本、累计审计回合数和每轮稳定指纹。建立或重构应用/运行时底座时再提供 `AC-0` 至 `AC-8` 闭包账本、到矩阵项及 `path:symbol/T-` 的映射和所有不适用证据。指纹在审计期间变化则该轮作废并重新冻结。

不要复制完整仓库、完整聊天或无关日志。默认只使用本地 Git、搜索、代码、项目证据和可重复命令；不得为了补强结论自动调用 MCP、网页、桌面控制或外部模型。

任务包只发送清单、映射、摘要、精确路径和关键原始失败行；审计者先读入口、公共契约、失败路径和触发维度，再按需打开逻辑承载文件。无基线新项目必须让每个 `R-/F-` 都有审计证据，但不复制或重读生成物、依赖、纯样板和已由确定性检查覆盖的机械内容。

## 普通单次全维审计

若用户已运行且合格的普通原生 `/review` 已被采纳，以下要求由其输出满足；否则创建一个与架构设计者和实现者独立的 SOL 审计代理，使用 `fork_turns: "none"`、`gpt-5.6-sol`、`max`。审计者不得修改产品代码、配置、迁移、测试或项目索引；只允许在预先指定的审计报告路径写入结果，并在同一任务中完成：

### 五项核心维度

1. **缺陷与正确性**：边界值、空值、错误处理、状态转换、资源生命周期、并发/竞态、数据损坏、调用者影响和回归。只报告可触发且影响行为的问题。
2. **功能完整性**：双向核对 `R- → 实现 → T-` 与 `diff → R-/明确必要工程工作`；覆盖正常、失败、恢复、跨功能交互、用户可观察行为和明确非目标。
3. **验证可信度**：检查测试是否真正覆盖验收和风险路径、断言是否有效、测试是否可能误通过、环境/夹具是否失真，以及手工验证能否重复。通过测试不能替代需求覆盖，新增代码也不要求机械追求覆盖率数字。
4. **性能与资源**：检查复杂度、关键路径 I/O/网络/数据库次数、内存/句柄、批量规模、缓存失效、并发吞吐及外部服务/计算成本。只有测量、剖析、可复现实验或明确数量级证据才能给出性能阻断；无相关变化时只写“未发现触发项”。
5. **架构与集成**：检查模块边界、依赖方向、职责、公共契约、数据流、生命周期、失败隔离/恢复、跨模块组合和需求已证明需要的扩展缝。只阻断系统性耦合、契约破坏、不可恢复失败或明显妨碍当前需求演进的问题，不推动风格性重构。

### 按变更触发的专项维度

6. **兼容与数据迁移**：公共 API、事件、文件/协议/数据库格式、旧配置、升级降级、幂等、回填、回滚和历史数据；仅在契约或持久数据变化时展开。
7. **可靠性、可运维性与可观察性**：启动/关闭、重试/超时/限流、故障隔离、日志/指标/诊断、配置缺失、备份恢复、部署与回滚；仅在服务、后台任务、外部依赖或运行流程变化时展开。
8. **用户体验与无障碍**：关键用户流程、反馈状态、错误提示、键盘/焦点、可读性、响应布局、平台惯例和必要本地化；仅在用户界面、CLI 交互或面向用户输出变化时展开。
9. **可维护性与变更安全**：重复业务规则、隐式耦合、不可理解控制流、死代码、错误抽象、索引/日志失真，以及使下一次修改容易破坏行为的结构；只报告会实质提高缺陷概率或修改成本的问题，不报命名/格式偏好。
10. **依赖、平台、构建与交付**：依赖增删/升级、运行时/操作系统差异、构建可复现性、配置默认值、安装升级卸载和发布产物；仅在相应文件或交付方式变化时展开。
11. **安全、隐私与合规**：明确需求或变更直接触及认证、权限、秘密、个人数据、外部输入或法规约束即触发最小范围、低优先级维度审计；只覆盖被触发的信任边界、输入流和数据影响，不自动扩大为全域攻击面扫描或第三方插件审计。

### 统一判定

任何可复现的阻断/高风险缺陷、未满足验收、无效验证、不可接受的性能/成本回退、兼容或数据损坏、发布/恢复失败、关键体验不可用、公共契约破坏或架构级系统风险均不通过。证据不足写明未验证范围和所需证据，不得把未知写成通过。一个问题只归入主维度，必要时标注关联维度，禁止重复报告。

普通任务不得按维度、功能、文件或工具结果拆分审计代理，也不得再启动内容相同的第二轮自由式审计。先运行项目已有的测试、类型检查、静态分析，以及被触发维度所需的基准、剖析、构建或界面验证，再把全部结果一次性交给同一审计者；工具不能取代语义判断。底层任务的重复审计仅按 foundation-gate 的完整闭环进行，每轮仍只有一个统一审计 SOL。

## 专项工具门

- 规格一致性、代码图、静态分析、基准或剖析工具仅在已有输入且预计会改变发布结论时使用。不得为了形式完整自动安装、全仓扫描或生成大报告。
- 不主动寻找或调用安全审计插件。追加安全工具检查前，任务包必须同时列出：具体信任边界；精确输入/数据 `path:symbol`；现有测试缺失的明确断言；仅限这些路径的允许检查/命令；该证据会改变的交付判定。五项不全时只用现有代码和测试完成已触发的安全维度，缺证据处标记 `UNKNOWN`，不得调用额外工具。五项齐全时只允许一次所列范围检查，仍并入本轮审计且不增加第二个 SOL；第三方插件或全域扫描只有用户明确点名插件和精确范围时才允许。
- 工具失败表示该专项未知，不得伪装成通过；不影响其他维度继续审查。

## 输出、修复与复审

- 每个普通或底层问题必须包含编号、严重度、`路径:行`、触发条件、影响和证据；任何 FAIL 都必须附 [dispatch-contracts.md](dispatch-contracts.md#sol-审计修复契约) 的全部字段，包括唯一执行者和能力门证据，拒绝无定位的通用建议、最小提示或开放式选择。主控只能补充最新指纹/证据和文件所有权，不得摘要、弱化或改写审计 SOL 的已决方案。
- 每个完整交付只维护一份报告：优先使用仓库既有审计目录；不存在时使用 `docs/ai/audits/AR-YYYYMMDD-01-简名.md`。报告给出五项核心状态、专项触发表和一个总判定；不适用专项只保留一行原因。复审更新同一报告的问题状态和最终判定，不另建报告。若原生审查不能写文件，由主控把其结构化结果保存到该路径，不再调用模型改写。重大改动日志只链接报告，不复制正文。
- 对用户只汇报判定、CRITICAL/HIGH 和必要的未决风险；其余留在报告，避免重复 token。
- 普通修复后先累计全部关闭证据，再以所有未关闭问题编号为一个任务，一次复审修改区域、相关调用者/契约和回归测试。仅当冻结指纹在范围外变化时扩大复审。底层修复后必须重跑确定性门、重冻结，并由同一独立审计角色再次完整统一审计；每轮更新不可重置的回合/问题账本：有客观进展时继续，首个完整无进展轮只允许一次最终收敛尝试，连续第二个无进展轮按 foundation-gate 标记 BLOCKED。
- 普通任务核心维度均无阻断或高风险问题、全部触发专项已关闭、功能验收有证据且适用验证成功，才可判定“通过”。底层任务还必须满足 foundation-gate 的 1-14 矩阵适用项全 PASS、无 UNKNOWN、确认问题全关闭、确定性检查通过、指纹稳定，并同时声明架构门和实现门 PASS。
