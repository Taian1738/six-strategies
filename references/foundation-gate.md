# 底层架构双门与收敛协议

适用协议：`LT-2026-08-21.11`

仅在 [SKILL.md](../SKILL.md) 的“底层架构触发”命中时读取。普通功能不套用本文件的模型、门禁或无上限收敛规则。

## 触发边界

“底层架构”是新建或重构以下任一底座：

- 新项目骨架；
- 模块系统；
- 跨模块公共契约或公共接口底座；
- 全局生命周期或资源所有权底座；
- 持久化或迁移基础设施；
- IPC/事件总线底座；
- 权限底座；
- 插件系统；
- 运行时、构建或发布底座。

普通 API 方法/端点、单个模块、局部生命周期、业务功能、局部 UI、单点修复、局部性能优化，以及不改变上述底座契约的功能迭代不触发本协议；它们按普通风险路由。运行时/构建/发布类任务只有建立或重构共享构建图、依赖闭包机制、产物组合根、发布 gate、更新/回滚流水线或平台抽象时才属于底座；单个依赖、版本、配置键或产物成员变化若不改变这些机制及契约，不触发本协议。事实不足时先用 `LUNA_FACT_GATE` 收集精确构建入口、清单和调用证据，再由主控/SOL唯一判定，不得因关键词自动升级。命中一个底座触发项才按底层任务处理；架构门和实现门都必须 PASS。

混合交付中，普通功能只要依赖、改变或验证底层契约，或与底层重构共享写集、运行状态、迁移、集成验收，就并入同一底层冻结变更集。拆出普通任务必须同时提交四项可复核证据：公共契约/调用依赖交集为空；精确文件与符号写集不重叠；进程、端口、锁、数据库、迁移、缓存及其他状态资源不共享；两部分可分别执行验收且无需对方产物。任一项重叠、未知或只有口头声明时必须并入；不得为降低门禁而人为拆分。

## 固定角色和阶段

| 阶段 | 角色与模型 | 权限和输出 |
|---|---|---|
| 可实施性取证 | Luna `max`（`LUNA_FACT_GATE=PASS`）+ 设计 SOL 核验 | Luna 只读抄录入口、调用边、现存声明/配置、测试和工具原始结果，只返回 `FACT/CONFLICT/UNKNOWN`；不得形成契约、风险、安全或长程状态结论。设计 SOL 独立核对来源并完成全部语义归纳。 |
| 架构设计与冻结 | SOL Codex `ultra` | 依据证据设计并冻结模块边界、接口、不变量、失败路径、依赖顺序、能力门证据和执行者。 |
| 架构契约门 | 与设计者独立的 SOL Codex `ultra` | 统一审计架构契约；不得按维度、组件或文件拆审。该角色在后续实现审计中保持独立并连续复用。 |
| 搭建与实现 | Luna `max` 或独立实现 SOL `max` | `LUNA_GATE=PASS` 的有界批次交 Luna；无法继续冻结的最小不可分关键切片交与设计者/审计者分离的实现 SOL。 |
| 实现审计与返修 | 同一独立审计 SOL Codex `ultra` + 契约指定执行者 | 每轮冻结后由同一审计角色覆盖完整矩阵；FAIL 时先产出唯一完整修复契约和执行者判定。 |

SOL 架构设计、关键实现和架构契约审计必须由相互独立的角色承担；同一代理不得既写产品文件又终审。实现冻结后保持同一审计角色、报告、矩阵和问题编号，不得靠换审计者重置未关闭问题；时间紧邻且上下文可靠时复用原审计代理，长暂停、压缩、不可用或新建最小闭环包更省输入时可更换为新的独立 SOL。替换只改变执行实例，不重置审计角色、报告、指纹、问题编号或 append-only 回合账本，且新实例必须先读取这些完整证据。每轮只有一个统一审计 SOL，审计代理在无输入等待期间不得空置。

模型和执行模式按 [SKILL.md](../SKILL.md) 的固定映射及可用性状态预检。底层所需 SOL、Luna、Codex `ultra` 或审计独立性任一不可用时只标记 `BLOCKED`（原因码 `BLOCKED_MODEL`），不得同时写 `NEEDS_USER`；解除条件可包含恢复能力，或由用户另行改变任务契约。独立实现 SOL 只承接内容本身未通过 Luna 能力门且无法继续冻结的关键切片，不得作为 Luna 模型不可用的回退。底层不得使用普通任务的 `DEGRADED` 单代理路径、定性“等价模型”或静默回退。

## 双门流程

1. Luna `max` 只按 `LUNA_FACT_GATE=PASS` 的有界取证包收集白名单事实；一旦需要跨模块语义、信任边界或长程状态推理即停止。设计 SOL 独立核对原始定位并形成相关结论，再为任何写入批次运行 `LUNA_GATE`。
2. SOL Codex `ultra` 设计、编号并冻结架构契约、`R- → A- → F- → T-` 批次、每批 `LUNA_GATE` 证据和执行者；`WANXIANG_ROUTE=ON` 时直接按当前 `$wanxiang` 完成 GUI 专项契约并并入同一架构冻结集，`OFF` 时不加载万相且保持现有视觉体系，`N/A` 时确认任务无 GUI 工作并跳过全部 GUI 契约。
3. 独立 SOL Codex `ultra` 对架构契约运行一次统一全维架构审计。架构门 FAIL 时，该审计 SOL 先交付唯一完整修复契约；能力门通过的文档批次由 Luna `max` 修改，未通过的架构决定由原设计 SOL Codex `ultra` 修订。重新运行确定性门、重新冻结，再由同一审计角色复审。未 PASS 不得搭建。
4. 架构门 PASS 后，能力门通过的有界批次由 Luna `max` 搭建；无法继续冻结的最小不可分关键切片由独立实现 SOL `max` 完成；主控只整合不改变冻结决定。
5. 实现集、测试、索引、构建/发布证据和任务范围指纹稳定后，冻结变更集并运行确定性门。
6. 同一独立审计 SOL Codex `ultra` 每轮对冻结变更集运行一次完整统一全维审计；不得拆分审计。
7. PASS 必须同时满足实现门条件。FAIL 时审计 SOL 先给出 [SOL 审计修复契约](dispatch-contracts.md#sol-审计修复契约)，其中必须包含能力门证据和唯一执行者；Luna `max` 只执行通过门的有界批次，其余最小不可分关键切片由独立实现 SOL `max` 执行。之后重新运行确定性门、重新冻结指纹，再由同一审计角色完整复审。
8. 只要存在可执行进展就继续第 7 步；直到 PASS 或按“BLOCKED”条件停止。不得伪造 PASS，也不得以普通 SOL 回合上限停止底层门。

架构门和实现门的确定性检查、审计矩阵、修复契约、回合记录和最终指纹必须落在任务证据中。审计 SOL 必须合并同一根因导致的相互冲突问题，交付一个有序批次；主控不得摘要弱化契约。维护 append-only 回合账本：每轮记录指纹、问题 ID、状态变化、修复批次、确定性结果和客观进展；问题 ID 只增不删、不重编号，替代问题用 `supersedes` 关联，不得因更换代理或报告改写而重置。

## 应用架构最小闭包

建立或重构可运行应用、服务、CLI、桌面/移动端、嵌入式程序、插件宿主或发布运行时时，架构契约必须用一份紧凑账本逐项冻结 `AC-0` 至 `AC-8`；纯库或不触及相应运行边界的任务可将具体项标为不适用，但必须提供可验证的非触发证据。账本先记录基线提交/版本、时间、适用平台和范围指纹；旧架构快照、旧任务输出或文档只作线索，必须与当前代码、已批准决定和测试交叉核对，冲突或无法确认时标记 `UNKNOWN`。

| ID | 必须冻结的应用架构契约 |
|---|---|
| `AC-0` 最小性准入 | 每个新增模块、服务、公共接口、进程/通信桥、插件点、队列、缓存、配置项或依赖都关联当前 `R-` 和已验证的需求、约束、失败场景或负向探针；初建项目不要求先制造既有故障。写明 Ponytail 阶梯中现有实现、标准库、平台/框架原生能力及已安装依赖为何不能满足，以及删除/复用方案、最小 seam、已知上限和可测升级触发器。单实现接口、预留工厂、未来插件层或未使用脚手架默认删除；只有真实的信任、生命周期、替换、跨平台或测试边界才能例外。 |
| `AC-1` 拓扑与所有权 | 冻结系统上下文、仓库/模块依赖方向、进程/线程/worker/外部系统拓扑、组合根和每类资源/数据的唯一 owner；图不是必需，能无歧义表达 owner、依赖和调用方向的最短表格即可。 |
| `AC-2` 权威状态与契约层级 | 每个可变状态只有一个权威来源和提交者；读取、发现、选择、写入分别定义，调用方不得从 argv、URL、环境变量、缓存副本或其他旁路猜测权威值。公共稳定、受支持扩展、内部实现和启动私有事实分层，消费者只依赖获准 contract；稳定 contract 使用独立 DTO/错误/窄接口，不泄漏 provider class、平台 handle 或 bootstrap，`type-only import` 不能代替 package/export 隔离。跨作用域隐藏依赖和复制第二份 feature state 均禁止。 |
| `AC-3` 边界、载体与副作用 | 冻结进程/网络/权限/租户等信任边界、认证/授权和输入验证点及唯一数据载体；现有 HTTP/RPC/事件/IPC/数据库通路能承载时不得另造平行桥或同步副本。网络位置、loopback、同源或 Origin 校验不能单独充当跨信任边界的高权限调用认证；文件、安装、重启等能力若跨进程、网络或插件信任边界暴露，需与会话/短期 capability 或等价身份绑定，并冻结 issuer、audience/resource、generation/epoch、expiry、one-shot/replay、revocation、rate-limit 窗口和错误语义；同进程同 owner 且没有边界的内部调用不伪造 capability。全局 PATH、shell、用户配置、机器级状态及真实外部系统不得被环境式隐式修改；副作用限定在明确 owner 和用户授权范围。 |
| `AC-4` 组合、注册与兼容 | 冻结启动顺序、provider/registry key 的唯一注册 owner、重复注册的幂等或确定性拒绝语义、注销/cleanup 和兼容降级路径。文档或未来 scaffold 在实现和验证存在前不得声明可加载入口；“万物皆插件”只在当前需求确实需要独立替换、第三方扩展或运行时组合且已有框架 seam 时采用，否则直接组合。共享插件组合路径不代表同一权限或信任边界，in-process plugin 也不视为 sandbox；高权限 bootstrap、原生 handle 和通用 argv/locator 不得伪装成普通扩展能力。 |
| `AC-5` 代际生命周期 | 只有 restart/reload/profile/workspace/mode 切换实际导致运行时资源、权限或持久化作用域重建时，才冻结 generation/epoch；纯数据选择或原地配置刷新明确 N/A。触发后，服务引用、窗口、监听器、锁、缓存、事务和子进程句柄不得跨代缓存，旧引用必须失败关闭。每类资源只有一个 owner，资源取得后立即登记释放，首个副作用起就由 `finally`/等价机制覆盖；释放幂等、按依赖逆序、覆盖异步 mutation 的取消、drain、超时、部分提交恢复和完整子进程树，并有重复关闭、永久 pending 与每个部分启动点的失败验证。旧 handle 拒绝新调用不能替代证明旧 operation 已停止。 |
| `AC-6` 切换、健康提交与恢复 | 配置、profile、模式、插件、迁移或更新切换一旦跨运行时重建、持久化、外部副作用或不可逆边界，就使用明确状态机；纯进程内、可直接撤销且无共享状态的切换明确 N/A。`prepare/validate` 仅在存在候选状态时触发，`persist/commit` 仅在存在 durable state 时触发，`quiesce` 仅在旧运行时或共享副作用需排空时触发，`restart/reload` 仅在真实重建时触发，`health` 仅在候选需被接纳为可服务/可用状态时触发，`last-known-good/rollback` 仅在存在可保留候选或 before-image 时触发；不可回滚边界必须冻结 manual-recovery 状态而不是伪造 rollback。“进程退出 0”或“页面已加载”不能替代领域健康。健康 gate 明列所有必需且带 generation 身份的独立信号，只有 owner 能执行一次单调 durable commit；迟到、旧代或仅用于诊断的 evidence 不得改写提交或授予恢复权限。并发同目标如何合并、冲突目标如何拒绝、持久化失败如何释放、提交后重启失败如何重试、恢复何时需用户授权都必须唯一确定。 |
| `AC-7` 运行时与发布物闭包 | 按下方适用性子表，从真实产物枚举所有可达生产依赖、动态入口、资源、原生二进制、配置、运行时和许可证/notice，不以源码树、staging 目录或依赖名去重代替物理闭包。在干净环境验证实际 package/可执行文件/安装包/镜像/函数 bundle 的适用生命周期；签名、digest/hash、publisher、SBOM 或等价物理闭包清单、更新/部署清单仅在对应分发通道存在时与产物绑定。所有发布入口执行同一基线闭包 gate 及各自声明的平台/通道专项 gate，不得绕过适用检查。 |
| `AC-8` 可执行不变量与新鲜度 | 能机械表达的依赖方向、公开导出、注册唯一性、schema/version、运行时闭包、产物内容和平台矩阵必须进入确定性检查，而不只写在文档。架构证据携带基线和范围指纹；当前代码、清单、产物、测试或已批准决定变化后旧 PASS 自动失效并重新冻结。 |

### `AC-7` 适用性

`AC-7` 按子条件判定，存在任一运行时、部署根或分发产物时不得整项写 N/A：

| 场景 | 必审子条件；其余子条件逐项给 N/A 证据 |
|---|---|
| 不分发、无可执行运行时的纯源码库 | 可整项 N/A；一旦发布 package，则审 package 物理依赖/导出/资源闭包、干净消费者安装与最小调用、版本兼容、许可证/notice。 |
| 内部服务或 CLI | 审实际部署根/可执行产物的物理运行时闭包、干净环境启动与健康、升级/回滚和数据兼容；仅外部签名、公共更新通道、安装/卸载等确实不存在的子项可 N/A。 |
| 桌面/移动应用或系统安装包 | 审实际签名产物、clean-machine 首次启动、升级/降级/卸载、数据保留、失败回滚、publisher/hash/update manifest、许可证/notice 和全部发布入口 gate parity。 |
| 容器、镜像或 serverless bundle | 审 image/bundle 物理闭包、digest/签名、SBOM 或等价清单、许可证/notice、干净拉取/部署/启动/健康与部署回滚；安装器子项只在真实存在时触发。 |

审计映射固定为：`AC-0→1/10/14`，`AC-1→4/5/6`，`AC-2→2/3/5/7`，`AC-3→2/3/5/6/8/11/12`，`AC-4→4/6/8/14`，`AC-5→2/4/5/6/8/12`，`AC-6→2/3/5/6/7/8/9/11/12`，`AC-7→7/9/11/12/13`，`AC-8→1/9/13/14`。任一适用 `AC-*` 缺少精确 owner、状态/接口、实现落点和确定性证据时，其映射矩阵项不得 PASS；不得把重复文字或架构图数量当作完整度。

## 强制统一审计矩阵

每轮必须逐项给出 `PASS`、`FAIL` 或 `UNKNOWN` 及证据；矩阵不得按组件或维度拆成多个审计代理。

| # | 维度 | 至少核对 |
|---:|---|---|
| 1 | 需求双向追溯 | 每个 `R-` 到架构/实现/验证，以及每项变更反向到 `R-` 或明确非目标。 |
| 2 | 接口清单完整度 | 每个接口的签名/schema、错误、异步、取消、所有权、生命周期和版本。 |
| 3 | 接口覆盖面 | 每个能力、调用方、实现和验证均有映射，且映射闭合。 |
| 4 | 框架组成完整性 | 启动、配置、注册、模块装配、运行时边界和关闭路径均有真实承载。 |
| 5 | 依赖方向和边界 | 依赖方向、层边界、反向依赖、共享状态和所有权无越界。 |
| 6 | 跨模块集成 | 公共契约、数据流、事件/IPC、错误传播、初始化顺序和组合行为。 |
| 7 | 兼容/演进/迁移/回滚 | 版本兼容、升级降级、迁移幂等、回滚边界和旧数据/旧调用方。 |
| 8 | 缺陷与失败安全 | bug、边界、部分失败、并发、重入、时序、原子性、幂等、资源释放和数据丢失。 |
| 9 | 测试真实性 | 关键正常/失败/恢复路径、失败注入、精确断言、隔离真实性和不可误通过性。 |
| 10 | 性能/资源/扩展性 | 复杂度、I/O、内存、句柄、并发吞吐、容量、扩展边界和可复现实测证据。 |
| 11 | 安全/隐私 | 信任边界、权限、秘密、外部输入、最小权限、隔离和敏感数据处理。 |
| 12 | 可靠性/恢复/可观察性/运维 | 启停、超时、重试、限流、故障隔离、恢复、日志/指标/诊断、备份和运维动作。 |
| 13 | 构建/平台/发布 | 依赖、运行时/平台差异、可复现构建、安装升级卸载、真实产物 identity/integrity/signature、许可证/notice、新鲜发布清单、入口 gate parity、发布和回滚。 |
| 14 | 维护性与项目索引真实性 | 控制流和抽象可维护，项目索引、接口清单、变更日志与实际代码一致。 |

未适用项也必须写明适用性依据；`UNKNOWN` 不能作为 PASS。任一确认问题未关闭、确定性门失败或任务范围指纹变化，门均不 PASS。

## 阶段化证据与防假通过

- 每轮先把原始用户需求、用户后续修改、明确非目标和约束作为不可省略的 source requirements；审计 SOL 必须独立核对 `原始需求 → R-` 是否完整，再检查 `R- → A-/F-/T-`。只审主控已列出的 `R-` 不足以 PASS。
- 每个矩阵项的 PASS 必须附：适用性触发结论、精确契约/代码 `path:symbol` 或文档章节、对应确定性命令/探针及关键原始结果；禁止以“测试已通过”“看起来兼容”或无定位摘要作为证据。
- 架构门只能证明契约级完整性：接口清单、状态机、失败矩阵、兼容/迁移/回滚设计、资源所有权、可执行验证设计和预算必须精确可实施；不得用计划中的测试冒充实现已验证。
- 实现门必须使用已执行的测试、失败注入、构建、兼容/迁移探针及适用的测量结果；仅有设计文档或待执行计划不得 PASS。
- `不适用` 必须由预定义触发表和可验证的非触发证据支持，例如需求、diff、依赖、数据、平台或信任边界清单明确未触发；遗漏、不确定或无法验证时标记 `UNKNOWN` 或 `FAIL`，审计 SOL 可以驳回主控的 N/A。

## 确定性门与 PASS

架构门或实现门任一轮 FAIL 都必须先由审计 SOL 产出唯一、无备选、实现完整的修复契约和执行者判定；不得跳过契约直接写入或让主控/Luna代替审计 SOL 作产品、架构、接口或算法选择。每轮在 SOL 审计前固定并记录：协议版本、任务范围文件清单/哈希、基线或前后清单、`R-/A-/F-/T-` 映射、接口清单、能力门证据、测试/静态检查/构建/发布命令及原始结果、未纳入范围的用户改动。必须重跑与本底座相关的确定性命令，不以审计文字替代命令证据。

架构门 PASS：架构契约完整、矩阵适用项全 PASS、无 UNKNOWN、确认问题全关闭、确定性架构检查通过、契约指纹稳定。

实现门 PASS：实现矩阵适用项全 PASS、无 UNKNOWN、全部确认问题关闭、确定性测试/失败注入/构建或发布检查通过、任务范围指纹稳定，并且架构契约仍与实现一致。最终 PASS 必须同时声明架构门和实现门 PASS。

## 收敛与 BLOCKED

底层架构质量门不受普通 SOL 四回合上限约束。每个新建的架构审计、实现审计或复审回合都计数并记录成本，但计数不是配额；存在客观进展时继续，完成一次修复并复审后的首个无进展轮只允许再做一次最终收敛尝试，连续第二个无进展轮立即 BLOCKED。

客观进展至少满足一项：确认问题经确定性证据关闭；未关闭问题的数量或最高严重度下降且没有新增同级/更高问题抵消；产品/契约/测试指纹按修复契约变化且对应失败探针由失败变通过；新的一手证据实质改变矩阵结论或唯一修复方案。仅改写报告、重命名问题、替换措辞、轮换审计者、加入不改变结论的证据或交替提出方案均不算进展。初始架构门/实现门 FAIL 只建立比较基线，无进展计数为 0；只有“执行修复 → 重跑确定性门 → 重新冻结 → 统一复审”这一完整闭环与前一 FAIL 基线相比仍无上述变化时，才记 1 个无进展轮。连续两轮无客观进展即 `BLOCKED`，不以“方案看起来不同”绕过。

每轮 FAIL 在尚未触发 BLOCKED 时必须先交完整修复契约，再派发契约指定的唯一合法执行者；写出、转交或重新措辞修复契约本身不算客观进展。回合账本显示已连续两轮无客观进展时，当前审计直接输出 `BLOCKED`、最后有效修复契约、阻塞证据和解除条件，不得再派发任何执行者来重置计数。

仅在以下情形明确标记 `BLOCKED`：

- 缺少用户授权或产品决定；
- 缺少会改变结论的外部事实；
- 必要工具证据不可得；
- 必需模型、Codex `ultra` 执行模式或独立审计角色不可用；
- 并发写入破坏任务范围指纹且无法恢复稳定冻结；
- 同一修复方案连续两次失败且审计 SOL 没有改变结论的新证据；或连续两轮没有上述客观进展。

BLOCKED 必须列出阻塞证据、解除条件、已尝试回合和未决矩阵项；不得改写为 PASS。阻塞解除后从确定性门重新开始并继续同一审计闭环。

## 审计输出

每轮统一输出必须包含：

```text
协议版本：LT-2026-08-21.11
门：架构契约门 | 实现门
回合：<架构门或实现门的序号；累计审计回合另记>
指纹：<任务范围指纹及稳定性结论>
结论：PASS | FAIL | BLOCKED
矩阵：<1-14 每项 PASS/FAIL/UNKNOWN/不适用及证据>
确认问题：<编号、严重度、精确位置、触发证据、状态>
确定性门：<命令、精确断言/结果、通过或阻塞原因>
修复契约：<FAIL 时逐项附完整 SOL 审计修复契约；PASS 时写无>
```
